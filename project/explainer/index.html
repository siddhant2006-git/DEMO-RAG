01

The job, before any software

Understand this and the rest of the architecture stops looking arbitrary.

A tender is a rulebook. A department publishes a PDF that says, in prose, who is allowed to bid: minimum turnover, a live GST registration, so many years of experience, not blacklisted.

A bid is a claim. A company sends back its own PDF describing itself: our turnover is ₹6.2 crore, our GSTIN is this, we have 8 years of experience.

An officer now has to do three things for every criterion in every bid: find the rule in the tender, find the matching claim in the bid, and — the expensive one — open the GST portal, the Udyam registry and the debarment list and check whether the claim is true.

One tender with 8 bidders and 27 criteria is 216 manual comparisons, plus a few dozen portal lookups. It takes days.

Under deadline pressure, the step that gets skipped is always the portal lookup — because it is the slow one. So a company that overstated its turnover wins a public contract, and six months later, when someone asks why it passed, there is nothing to show. The working notes were never a record.

TenderGuard exists to make that check cheap and to leave behind the record.

02

The one idea everything else follows from

If you remember one sentence about this codebase, make it this one.

The LLM extracts. It never decides.

Here is why that line is load-bearing rather than a slogan.

An LLM's answer is a plausible sequence of tokens. Ask it twice and you can get two answers. Ask it why and it will write you a paragraph that sounds like a reason but isn't one — it can't hand you the page it came from, because it never had a page, it had a probability distribution.

A procurement decision has the opposite requirement. Months later, someone will ask "why did this bid pass?" and "show me the line in the document." That answer has to be identical every time it is asked.

So the model is confined to a single job: turn a page of prose into typed values, each carrying the exact sentence it came from. Everything after that point is arithmetic on those values.

The line of YAML that decides it

Step 5 above is the entire point of the system, and it is controlled by one field on the rule. Flip it and watch the verdict flip with it.

What if the rule trusted the document first?interactive
source_priority:

Two words, swapped. One catches an overstated claim; the other rubber-stamps it. That is why source_priority lives in an officer-editable YAML file and not buried in Python — and why the finding stores both values side by side even though only one of them decided the outcome.

05

Rules are data, not code

An officer can add or change a criterion without a developer touching Python. Click any highlighted field.

A rule pack is one YAML file per tender category — backend/rules/default_goods.yaml, default_works.yaml, default_services.yaml. Here is the goods pack, in full, exactly as it ships.

backend/rules/default_goods.yamlclick a field →

        

        

      


      

        
The loader parses this with a line-tracking YAML loader, so a typo fails fast with a line number instead of a shrug. Every rule is validated for required fields, a known severity, a unique id, and having either value or threshold_from.

        
One detail worth pausing on: applies_if is parsed by a tiny hand-written grammar in rules/condition.py — never eval(). Rule packs are officer-editable data files. If eval() ran them, editing a procurement criterion would be arbitrary code execution.

        
Choosing the pack is by tender category, and an unrecognised category falls back to goods rather than erroring — a missing pack should degrade the specificity of the check, not the availability of one.

Try the demo bid: a CRITICAL turnover rule fails outright, and the score still lands in the LOW band, because five other rules passed and the failing one is only 25 of 105 weight.

        
The number is a triage aid. The matrix is the deliverable.

        
Now try debarred vendor. REQ-DEBARMENT has severity BLOCKER, and a failed BLOCKER forces the band to HIGH regardless of what the arithmetic says. One disqualifying fact should never be diluted by twenty-six unrelated passes — so it isn't averaged, it's overridden.

        
Rules whose applies_if is false are skipped entirely — no finding, and their weight leaves the denominator. Toggle the MSME switch and watch the total weight move from 105 to 115.

      

    


    
    

      

        
07

        

          
Fencing the model in

          
Stage 2 is the only untrusted band in the system. It has four fences around it.

        

      

      

        
Fence 1 — pinned decoding

        
Every call runs at temperature 0 with a fixed seed. The same page produces the same extraction. This doesn't make the model correct; it makes it repeatable, which is a prerequisite for debugging it.


        
Fence 2 — schema or nothing

        
JSON mode is forced, and the response is validated against a Pydantic schema. If it fails, llm/json_guard.py hands the model back its own bad output, the validation error and the schema, and asks it to fix it — up to two repairs, then it raises. It never returns a best-effort half-parse.


        
Fence 3 — the snippet must be real

        
Every extracted item has to carry the sentence it came from. snippet_guard.py checks that the sentence appears literally in that page's text — whitespace and case normalized, nothing else. A plausible paraphrase is rejected exactly as hard as an invention. Try it:

The third option is the interesting one. "minimum average annual turnover of Rs. 5 crore" is true, it is a fair summary, and it is thrown away — because the tender's actual words are "an average annual turnover of at least Rs. 5 Crore". The guard has no opinion about meaning. It only knows whether those characters are on that page. That bluntness is the feature: a rule that requires judgement to apply is a rule that can be argued with.


        
Fence 4 — one place strings become numbers

        
"Rs. 6,20,00,000", "6.2 Cr", "62 lakh", "₹5,00,00,000/-". Indian currency prose is a small parsing nightmare, and it is handled in exactly one file — extraction/normalizers.py — before anything is stored. Type anything into the box:

By the time a value reaches the rule engine it is a float. Nothing downstream ever parses a string, so nothing downstream can disagree about what "5 Cr" means.

        
Four fences, one purpose: whatever the model emits is an input to the system, never an output of it.

Five things worth trying

        
    
          
  • Pick the demo bid. REQ-TURNOVER fails on 4.1 Cr even though the bid says 6.2 Cr — and the matrix shows both, with the government value marked as the one that decided.
    • 
          
  • Pick GST portal unreachable, and read the result carefully. REQ-GST-ACTIVE lists only [government], so with no government value it drops to review. But REQ-TURNOVER lists [government, document] — so it falls through to the vendor's own claim, and the inflated 6.2 Cr now passes. A dead portal never invents a verdict, but it does hand the decision back to the document. Worth knowing before you demo it.
    • 
          
  • Clear tender.turnover_requirement. The rule can't resolve its expected value, so it reports review rather than guessing a threshold.
    • 
          
  • Break the PAN (delete a character). The fact normalizes to None and is dropped entirely, so REQ-PAN reports "no value found" — a real behaviour that surprises people who expect a FAIL.
    • 
          
  • Turn on the conflict switch, then watch which rules react. REQ-EXPERIENCE reads [document], so the contradiction is what it sees and it goes to review. REQ-TURNOVER resolves from the government record first, so the bid contradicting itself never even gets looked at. The conflict rule only bites on facts the document actually decides.

09

        

          
Where the retrieval actually sits

          
This is a RAG-shaped system. Be precise about which part is the RAG, because it isn't the part you'd guess.

        

      

      

        
There is a full retrieval stack in services/retrieval/ — chunker, embedder, vector store, search. Here is what it does, and then the important part: where it does not sit.


        
    
          
  • Chunking (chunker.py) — a chunk boundary opens at every heading the layout detector found; within a section, text splits again only past ~1500 characters, at a paragraph boundary where one exists. Each chunk keeps the page numbers it actually came from, so a hit can always be pointed at.
    • 
          
  • Embedding (embeddings.py) — all-MiniLM-L6-v2, 384 dimensions, normalized, running on CPU. The model is loaded once per process and cached, because the several-hundred-millisecond load would otherwise repeat on every call.
    • 
          
  • Storage (vector_store.py) — one FAISS index per document, written to data/vectorstore/<document_id>.faiss with a JSON sidecar for the chunk metadata. No vector database service to run, and deleting a document deletes its index.
    • 
          
  • Search (search.py) — top-k clause lookup: "find me the clause that proves X" inside one document.
    • 
        


        
And now the part that matters

        
Extraction is per page, not retrieval-driven. The rule engine reads typed facts from the database, not retrieved text. Indexing runs after ingestion and is explicitly allowed to fail without failing the ingest.

        
Retrieval is the officer's lookup aid. It is not in the verdict path.

        
This is a deliberate call, and it is worth being able to defend in a review. Classic RAG — retrieve chunks, stuff them in a prompt, let the model answer — puts the model back in the decision seat and reintroduces exactly the problem section 02 exists to eliminate. So retrieval was kept where it helps a human (finding a clause in a 90-page tender) and kept out of where it would hurt (deciding whether a bid passes).

        
Why per-document indexes rather than one big collection: an officer's question is always "in this tender", never "across all tenders ever filed". Scoping the index to the document makes the retrieval trivially correct and makes deletion trivially complete.

      

    


    
    

      

        
10

        

          
The data model

          
Eleven tables. Two invariants that are worth more than the other nine tables combined.

        

      


      

        
      


      

        
Invariant one — no finding without evidence

        
Evidence is 1:1 with Finding behind a unique foreign key, and a finding is never written without one. If the bid page can't be resolved, the code falls back to the tender page, then to page 1 — but it always lands on a real page of a real document, and it stores that document's SHA-256 alongside. A verdict you can't point at is not a verdict this system is willing to save.


        
Invariant two — no finding without a requirement

        
Finding.requirement_id always points at a real Requirement row. If extraction already produced one for this rule (matched by external_ref == rule.id), that one is used, page and snippet included. If not, compliance/requirement_binding.py synthesizes one from the rule pack itself. The compliance matrix therefore works before an officer has reviewed a single extracted requirement — which is what makes the tool usable on day one instead of after a review backlog.


        
Three things you'd only notice by reading the code

        
    
          
  • Every finding is stamped with the rule pack's name, version, sha256 and the engine_version. A report filed today stays re-derivable after someone edits the pack next month — you can tell which pack produced which verdict.
    • 
          
  • Re-running compliance replaces this bid's findings rather than appending. The engine is deterministic, so a history of runs would just be the same rows repeated; the matrix should show current truth.
    • 
          
  • All columns use dialect-generic SQLAlchemy types (Uuid, JSON — not postgresql.UUID / JSONB) so the identical models run on Postgres and on SQLite. Keep it that way when you add a model.

How it runs — and what happens when it can't

          
Eight containers is the intended shape. The more interesting design work is in what each one's absence does.

Ten sentences

          
If you had to explain this system in a corridor, these are the ten.

        

      

      

        
    
          
  1. An officer uploads a tender PDF and a vendor's bid PDF; the system decides whether the vendor is eligible and proves it.
    2. 
          
  2. The LLM extracts. It never decides.
    3. 
          
  3. Extraction is per page, at temperature 0, forced into JSON, schema-validated, and repaired up to twice before it fails loudly.
    4. 
          
  4. Anything the model returns whose source snippet isn't literally on that page is thrown away.
    5. 
          
  5. Messy strings become typed numbers in exactly one file, so nothing downstream parses text.
    6. 
          
  6. Government portals return UP, NOT_FOUND or DOWN — never a verdict — and a portal being down degrades a finding to NEEDS_REVIEW.
    7. 
          
  7. Criteria live in officer-editable YAML rule packs, and source_priority: [government, document] is how an overstated claim gets caught.
    8. 
          
  8. The rule engine is a pure function: no model, no database, no clock, no network — same inputs, same verdict, forever.
    9. 
          
  9. Every finding carries one evidence row — a real document, page, snippet and SHA-256 — plus the hash of the rule pack that produced it.
    10. 
          
  10. Every dependency in the system has a defined behaviour when it's missing, and it always fails toward a human rather than toward a confident wrong answer.
